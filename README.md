# AI Recruiter RAG

An AI-powered, role-based candidate screening system. A candidate uploads their resume, picks a target role, and goes through an adaptive technical interview — every question is generated live from a retrieval-augmented generation (RAG) pipeline grounded in role-specific reference material, not templated or pre-written.

## How it works

1. **Resume upload** — candidate uploads a PDF resume
2. **Resume parsing** — text is extracted (with OCR fallback for scanned pages) and structured into skills, technologies, domains, and experience level using Gemini
3. **Role selection** — candidate picks AI Engineer, ML Engineer, or Data Scientist
4. **Retrieval** — the resume's skills/tech + selected role are turned into search queries, run against a FAISS vector store built from 7 role-tagged reference books
5. **Question generation** — retrieved context + resume background are given to Gemini, which writes one grounded, non-generic question at a time
6. **Interactive interview** — candidate answers each question through the UI; the system tracks session state and avoids repeating questions
7. **Summary** — full transcript with each question's grounded source(s), for traceability

## Architecture

```
frontend/          Next.js (App Router, TypeScript, Tailwind) — single-page interview flow
backend/
  app/
    main.py         FastAPI app — session orchestration, all endpoints
    database.py     SQLite connection setup
    models.py       SQLAlchemy models (InterviewSession, QuestionAnswer)
    schemas.py      Pydantic request/response schemas
    services/
      resume_parser.py       PDF text extraction (OCR fallback) + Gemini structuring
      retrieval.py            Query construction + role-filtered FAISS search
      question_generator.py   Gemini-based grounded question generation
    notebooks/
      embedding_pipeline.ipynb  Colab notebook: ingests the 7 knowledge base books,
                                 chunks, embeds, and builds the FAISS index
  data/
    vectorstore/    index.faiss + chunks_metadata.json (built by the notebook)
```

## Setup

### Backend
```
cd backend
python -m venv venv
venv\Scripts\activate
pip install -r requirements.txt
```
Create a `.env` file in `backend/` with:
```
GEMINI_API_KEY=your_key_here
```
Run the server:
```
uvicorn app.main:app --reload
```
API docs available at `http://127.0.0.1:8000/docs`.

### Frontend
```
cd frontend
npm install
npm run dev
```
App available at `http://localhost:3000`. Requires the backend running simultaneously.

### Knowledge base (one-time setup)
The vector store (`index.faiss`, `chunks_metadata.json`) is generated by `backend/app/notebooks/embedding_pipeline.ipynb`, run in Google Colab against 7 role-tagged PDF textbooks stored in Google Drive. Run the notebook once, then download its two output files into `backend/data/vectorstore/`.

## Key design decisions

- **Role-tagged multi-book knowledge base.** Each of the 7 reference books is tagged to one of the 3 supported roles (AI Engineer / ML Engineer / Data Scientist) at ingestion time. Retrieval filters strictly by the candidate's selected role, so questions stay relevant to what they're actually being screened for.
- **OCR fallback during ingestion.** All 7 source PDFs contain a mix of real text and scanned image pages. Extraction tries real text first (fast) and only falls back to Tesseract OCR on pages that come back empty — avoiding unnecessary OCR cost while still capturing scanned content.
- **Front-matter skipping.** Table-of-contents and preface pages score deceptively high on embedding similarity despite having no real explanatory content. The ingestion pipeline skips each book's first ~30 pages before chunking to avoid grounding questions in table-of-contents listings.
- **SQLite over hosted Postgres.** Chosen deliberately over a hosted database (Supabase/Neon/etc.) to avoid free-tier usage caps and keep the project fully self-contained and reproducible — no external account dependency for graders running this locally.
- **Traceability.** Every generated question stores which source chunks it was grounded in, so the question → context link is auditable rather than a black box.

## Known limitations / possible extensions

- Question adaptivity currently cycles through a fixed query list per session rather than dynamically adjusting based on the quality of previous answers — a natural next step.
- Gemini free-tier rate limits (per-model daily caps) apply; a production deployment would move to a paid tier or add request queuing.
